## 1. 개요

### 1.1 목표
| 번호 | 목표 | 측정 지표 | 결과 |
|---|---|---|---|
| G1 | 장애를 사용자보다 먼저 탐지 | MTTD | 5분 37초 |
| G2 | 배포 결함 장애를 운영자 개입 없이 복구 | MTTR | 5분 38초 |
| G3 | 장애 원인을 한 화면에서 추적 | 로그·메트릭·트레이스 연계 | 대시보드 및 요청 ID 연계 구현 |
| G4 | 인프라 전체를 코드로 재현 | Terraform 관리 비율 | 44개 리소스 전량 |
| G5 | 월 운영비 2만원 이하 | AWS 청구액 | 약 1,600 ~ 5,800원 (산정치) |

### 1.2 범위
| 구분 | 포함 | 제외 |
|---|---|---|
| 애플리케이션 | 아이템 조회·생성 API | 사용자 인증, 프론트엔드 |
| 관측성 | 구조화 로그, 기본·커스텀 메트릭, 분산 트레이스, 대시보드 | 외부 APM, 로그 장기 보관 |
| 자가복구 | 배포 결함 시 정상 버전으로 자동 롤백 | 리전 장애 복구, 데이터 복구 |
| 배포 | CI/CD, 트래픽 전환 전 검증 | 카나리·블루그린 트래픽 분할 |

### 1.3 제약사항 및 가정
- 월 인프라 비용 2만원 이하 → 상시 실행 리소스(EC2, RDS, NAT Gateway) 사용 불가
- 서울 리전(ap-northeast-2) 단일 리전, 1인 개발·운영
- 장애의 주요 원인은 배포된 코드 결함이며, 데이터 스키마는 하위 호환을 유지합니다 (코드 롤백 시 데이터 불일치 없음).
- API Gateway HTTP API는 X-Ray를 지원하지 않으므로 트레이스는 Lambda 구간부터 수집합니다.

## 4. 상세 설계

### 4.1 적용 설계 원칙
| 원칙 | 적용 |
|---|---|
| 모듈화, 높은 응집도·낮은 결합도 | Terraform 모듈 4개가 각자 한 관심사만 담당하고, 모듈 간에는 출력값으로만 연결 |
| 관심사 분리 | 비즈니스 Lambda와 복구 Lambda 분리, 인프라(Terraform)와 코드 배포(CI) 소유권 분리 |
| 불변성 | 게시된 Lambda 버전은 변경하지 않으며, 롤백은 별칭(포인터) 전환으로 수행 |
| 멱등성 | 복구 Lambda는 현재 버전과 목표 버전이 같으면 조치하지 않음 |
| 실패 안전 | 배포 검증 실패 시 트래픽을 전환하지 않아 기존 버전이 계속 서비스 |
| 최소 권한 | 앱·복구·CI plan·CI deploy 역할을 분리하고 대상 리소스를 한정 |

### 4.2 구성요소
| 구성요소 | 역할 | 주요 설정 |
|---|---|---|
| API Gateway (HTTP API) | 요청 수신·라우팅 | 10 rps / 버스트 20, JSON 접근 로그 (14일 보존) |
| 앱 Lambda | 비즈니스 로직 | Python 3.12, arm64, 256MB, 10초, Active Tracing |
| `live` 별칭 | 서비스 버전 포인터 | API 통합 대상 |
| DynamoDB `items` | 데이터 저장 | On-Demand |
| CloudWatch 알람 | 장애 탐지 | 3종 (4.4 참고) |
| EventBridge 규칙 | 롤백 트리거 | 5xx 비율 알람의 ALARM 전환만 매칭, 재시도 2회 |
| 복구 Lambda | 자동 롤백 | 128MB, 대상 별칭 조회·수정 권한만 보유 |
| SSM Parameter | 롤백 대상 버전 저장 | `/obs-app/dev/last-known-good-version` |
| SNS, Budgets | 통보, 비용 경보 | 이메일, 월 $10 |

### 4.3 데이터 및 인터페이스
**`items` 테이블** — 접근 패턴이 ID 단건 조회뿐이므로 보조 인덱스를 두지 않습니다.

| 속성 | 타입 | 설명 |
|---|---|---|
| id (PK) | String | UUID v4, 서버 생성 |
| createdAt | String | ISO 8601, 서버 생성 |
| status | String | `active` / `archived` |
| payload | Map | 사용자 데이터 (최대 10KB) |

**API**

| 메서드 | 경로 | 성공 | 오류 |
|---|---|---|---|
| GET | `/health` | 200 `{"status":"ok","version":"N"}` | — |
| POST | `/items` | 201 `{"id","createdAt"}` | 400 `INVALID_JSON`, `INVALID_PAYLOAD`, `PAYLOAD_TOO_LARGE` |
| GET | `/items/{id}` | 200 아이템 | 404 `NOT_FOUND` |

오류 응답 형식: `{"error": {"code", "message", "requestId"}}`

### 4.4 알람 설계
자동 조치 알람은 보수적으로, 알림 전용 알람은 민감하게 설정했습니다. 모든 알람은 트래픽이 없는 구간을 정상으로 간주하며, SNS로 직접 통보합니다.

| 알람 | 조건 | 동작 |
|---|---|---|
| ① 5xx-rate | 5분 합계 요청 10건 이상이고 5xx 비율 5% 초과, 2회 연속 | 자동 롤백 + 이메일 |
| ② 5xx-count | 5분 합계 5xx 3건 이상 | 이메일 |
| ③ p99-latency | p99 3초 초과, 3회 중 2회 | 이메일 |

- ①은 요청 수 조건으로 저트래픽 구간의 오탐(요청 1건 실패 = 100%)을 방지합니다.
- ②는 ①이 판단하지 못하는 저트래픽 구간의 장애를 보완합니다.

### 4.5 자가복구 흐름
```
결함 버전 배포 → 5xx 증가 → ① 알람 ALARM 전환 → EventBridge → 복구 Lambda
  → SSM에서 롤백 대상 버전 조회
  → 현재 버전 = 대상 버전 : 조치 없음, 운영자 통보 (코드 외 원인으로 판단)
  → 현재 버전 ≠ 대상 버전 : live 별칭 전환 → 결과 로그 기록 및 운영자 통보
```

### 4.6 배포 파이프라인과 소유권 분리
| 단계 | 내용 |
|---|---|
| PR | ruff, pytest, `terraform fmt`/`validate`/`plan` → plan 결과 PR 코멘트 (읽기 전용 역할) |
| main 병합 | 테스트 → `terraform apply` → 코드 업로드 및 버전 게시 → 해당 버전 직접 호출로 검증 → 통과 시 `live` 전환 및 `last-known-good` 기록 |

| 대상 | 관리 주체 | 방식 |
|---|---|---|
| 인프라 전반 | Terraform | `apply` |
| Lambda 코드 | CI | Terraform은 최초 생성만 수행 (`ignore_changes`) |
| `live` 별칭 버전 | CI, 복구 Lambda | Terraform은 변경을 무시 (`ignore_changes`) |
| `last-known-good` 값 | CI | Terraform은 파라미터 생성만 수행 |

이 분리로 자동 롤백 이후 `terraform apply`를 실행해도 롤백이 되돌려지지 않습니다.

## 1. 개요

### 1.1 배경 및 문제 정의
소규모 서비스 운영에서 장애 대응은 보통 다음 순서로 이루어진다.

> 장애 발생 → 사용자 제보 또는 우연한 발견 → 로그 수동 확인 → 원인 추정 → 수동 롤백

이 방식은 **탐지 지연**(모니터링 부재), **진단 지연**(로그·메트릭·트레이스 분산), **복구 지연**(사람 개입 필수)이라는 세 가지 병목을 가진다. 특히 야간·주말처럼 운영자가 즉시 대응할 수 없는 시간대에 장애가 길어진다.

### 1.2 목표
| 번호 | 목표 | 측정 지표 |
|---|---|---|
| G1 | 장애를 사람보다 먼저 탐지한다 | 탐지 시간 (MTTD) |
| G2 | 배포 결함으로 인한 장애를 사람 개입 없이 복구한다 | 복구 시간 (MTTR) |
| G3 | 장애 원인을 한 화면에서 추적할 수 있게 한다 | 로그·메트릭·트레이스 연계 여부 |
| G4 | 인프라 전체를 코드로 재현 가능하게 한다 | `terraform apply` 1회로 전체 구성 |
| G5 | 월 운영비를 1~2만원 이하로 유지한다 | AWS 청구액 |

### 1.3 범위
| 구분 | 포함 (In Scope) | 제외 (Out of Scope) |
|---|---|---|
| 애플리케이션 | 아이템 조회/생성 REST API | 사용자 인증, 프론트엔드 UI |
| 관측성 | 구조화 로그, 기본·커스텀 메트릭, 분산 트레이스, 대시보드 | 외부 APM(Datadog 등), 로그 장기 보관 |
| 자가복구 | 배포 결함 시 이전 정상 버전으로 자동 롤백 | 인프라 장애(리전 장애) 복구, 데이터 복구 |
| 배포 | CI/CD 파이프라인, 배포 전 스모크 테스트 | 카나리/블루그린 트래픽 분할 |
| 환경 | dev 단일 환경 | 다중 환경(stg/prod), 다중 리전 |

### 1.4 이해관계자
| 이해관계자 | 관심사 |
|---|---|
| 운영자(본인) | 장애 자동 탐지·복구, 낮은 운영 부담 |
| API 사용자 | 가용성, 응답 속도 |
| 채용 담당자·면접관 (포트폴리오 독자) | 설계 근거, 기술 선택 이유, 재현 가능한 시연 |

## 2. 현행 분석 (AS-IS / TO-BE)

| 단계 | AS-IS (일반적 소규모 운영) | TO-BE (본 시스템) |
|---|---|---|
| 탐지 | 사용자 제보, 수동 확인 | CloudWatch 알람이 1분 단위 메트릭으로 자동 탐지 |
| 통보 | 없음 또는 수동 공유 | SNS 이메일 자동 발송 |
| 진단 | 서버 접속 후 로그 grep | 대시보드 + 구조화 로그 검색 + X-Ray 트레이스 |
| 복구 | 운영자가 이전 코드로 재배포 | 복구 Lambda가 별칭을 이전 정상 버전으로 자동 전환 |
| 배포 | 수동 업로드, 검증 없음 | GitHub Actions + 전환 전 스모크 테스트 |
| 인프라 관리 | 콘솔 클릭 (재현 불가) | Terraform 코드 (재현 가능, 변경 이력 추적) |
| 인증 정보 | 장기 Access Key를 CI에 저장 | OIDC 임시 자격증명 |

## 3. 요구사항 명세

### 3.1 기능 요구사항 (Functional Requirements)

| ID | 요구사항 | 상세 | 우선순위 |
|---|---|---|---|
| FR-01 | 헬스 체크 | `GET /health` 호출 시 상태와 현재 서비스 버전을 반환한다 | 필수 |
| FR-02 | 아이템 생성 | `POST /items`로 아이템을 생성하고 ID를 반환한다 | 필수 |
| FR-03 | 아이템 조회 | `GET /items/{id}`로 아이템을 조회한다. 없으면 404 | 필수 |
| FR-04 | 입력 검증 | 잘못된 요청 본문은 400과 오류 메시지를 반환한다 | 필수 |
| FR-05 | 구조화 로깅 | 모든 요청을 요청 ID가 포함된 JSON 로그로 기록한다 | 필수 |
| FR-06 | 메트릭 수집 | 요청 수·에러 수·지연시간을 수집하고, 업무 메트릭(`ItemsCreated`)을 기록한다 | 필수 |
| FR-07 | 분산 추적 | Lambda → DynamoDB 호출 구간을 트레이스로 기록한다 | 필수 |
| FR-08 | 대시보드 | 에러율·p99 지연·호출수를 한 화면에 표시한다 | 필수 |
| FR-09 | 장애 탐지 | 에러율·에러 건수·지연시간이 임계치를 넘으면 알람을 발생시킨다 | 필수 |
| FR-10 | 장애 통보 | 알람 발생 시 운영자에게 이메일을 발송한다 | 필수 |
| FR-11 | 자동 롤백 | 에러율 알람 발생 시 서비스 버전을 마지막 정상 버전으로 되돌린다 | 필수 |
| FR-12 | 롤백 통보 | 롤백 결과(이전/이후 버전, 원인 알람)를 이메일과 로그로 남긴다 | 필수 |
| FR-13 | 자동 배포 | main 브랜치 병합 시 인프라와 코드를 자동 배포한다 | 필수 |
| FR-14 | 배포 전 검증 | 새 버전은 스모크 테스트 통과 후에만 서비스에 투입한다 | 필수 |
| FR-15 | 변경 사전 검토 | PR 생성 시 테스트 결과와 인프라 변경 계획(plan)을 PR에 게시한다 | 권장 |
| FR-16 | 장애 주입 | 설정값(`FAULT_RATE`)으로 의도적 오류를 발생시켜 복구 과정을 재현한다 | 필수 |
| FR-17 | 비용 경보 | 월 예산의 50%·100% 도달 시 이메일을 발송한다 | 필수 |

## 4. 제약사항 및 가정

### 4.1 제약사항
| 구분 | 내용 |
|---|---|
| 비용 | 월 인프라 비용 1~2만원 이하 → 상시 실행 리소스(EC2, RDS, NAT Gateway) 사용 불가 |
| 인력 | 1인 개발·운영 |
| 기술 | Terraform ≥ 1.10, Python 3.12, GitHub Actions |
| 리전 | ap-northeast-2 단일 리전 |
| 서비스 특성 | HTTP API는 X-Ray를 지원하지 않음 → 트레이스는 Lambda부터 시작 |

### 4.2 가정
- 트래픽은 개인 포트폴리오 수준(월 10만 건 이하)이다.
- 장애의 주요 원인은 **배포된 코드의 결함**이다 (롤백으로 해결 가능한 유형).
- 데이터 스키마는 하위 호환을 유지한다 (코드 롤백 시 데이터 불일치 없음).
- 운영자는 이메일을 통해 알림을 받을 수 있다.

## 5. 타당성 분석

### 5.1 기술적 타당성
| 요구 기능 | 사용 기술 | 판단 |
|---|---|---|
| 불변 배포·즉시 롤백 | Lambda 버전 + 별칭 | 별칭 전환은 API 1회 호출로 즉시 반영 → 가능 |
| 장애 이벤트 연계 | CloudWatch Alarm State Change → EventBridge | 관리형 이벤트로 제공 → 가능 |
| 관측성 3요소 | CloudWatch Logs/Metrics, X-Ray, Powertools | 라이브러리 1개로 통합 구현 → 가능 |
| 키 없는 CI 인증 | GitHub OIDC + IAM Role | AWS 공식 지원 → 가능 |

### 5.2 경제적 타당성
6장 비용 분석 결과, 동일 기능을 서버 기반으로 구성할 때 대비 **월 비용이 약 1/20 이하**이며 예산 목표(2만원) 내 운영 가능 → 타당.

### 5.3 운영적 타당성
- 서버 패치·용량 관리가 불필요한 완전 관리형 서비스만 사용 → 1인 운영 가능
- 탐지·통보·복구가 자동화되어 운영자 상시 대기 불필요

## 6. 비용 분석

> 단가는 AWS 공개 요금 기준 근사치이며 서울 리전은 미국 리전보다 소폭 높다. 환율 1달러 = 1,400원 가정. 최종 수치는 AWS Pricing Calculator로 재확인한다.
> 계정 생성 시점에 따라 무료 티어 방식이 다르다 (2025-07-15 이후 생성 계정은 크레딧 방식). 아래는 **무료 티어를 전혀 적용하지 않은 보수적 계산**이다.

### 6.1 산정 기준 (평상시)
- 월 요청 10만 건, Lambda 메모리 256MB, 평균 실행시간 100ms
- 로그 수집량 월 0.5GB, 알람 3개, 대시보드 1개

### 6.2 서비스별 월 비용 (무료 티어 미적용)

| 서비스 | 산정 | 월 비용(USD) |
|---|---|---|
| Lambda 요청 | 10만 건 × $0.20/100만 | 약 $0.02 |
| Lambda 실행 | 10만 × 0.1초 × 0.25GB = 2,500 GB-초 × $0.0000167 | 약 $0.04 |
| API Gateway (HTTP) | 10만 건 × 약 $1.0~1.3/100만 | 약 $0.13 |
| DynamoDB On-Demand | 읽기·쓰기 10만 건 | 약 $0.10 |
| CloudWatch Logs | 수집 0.5GB × 약 $0.76/GB | 약 $0.38 |
| CloudWatch 알람 | 알람 지표 4개(①은 지표 2개 사용) × $0.10 | 약 $0.40 |
| CloudWatch 대시보드 | 1개 (3개까지 무료, 미적용 시 $3) | $0 ~ $3.00 |
| X-Ray | 기본 샘플링 약 1만 트레이스 × $5/100만 | 약 $0.05 |
| SNS 이메일 | 수십 건 | 약 $0 |
| S3 (Terraform state) | 수 MB | 약 $0.01 |
| **합계** | | **약 $1.1 ~ $4.1 (약 1,600 ~ 5,800원)** |

→ 무료 티어를 적용하면 대부분 0원이다. 무료 티어가 없어도 **NFR-07(평상시 5천원 이내)을 거의 충족**한다.

### 6.3 시나리오별 비용
| 시나리오 | 조건 | 예상 비용 |
|---|---|---|
| 평상시 | 월 10만 건 | 약 1,600 ~ 5,800원 |
| 시연 | `load.sh` 1회 최대 3,000건 × 월 10회 추가 | 증가분 100원 미만 |
| 최악 (공격·폭주) | 스로틀 상한 초당 10건 × 30일 풀가동 = 약 2,600만 건 | 약 $50 이상 → **Budgets 알림으로 조기 인지 후 API 스테이지 차단** |

### 6.4 대안 비교 (동일 기능 구성 시)

| 항목 | 서버리스 (채택) | EC2 + ALB | 컨테이너 (ECS Fargate) |
|---|---|---|---|
| 월 고정비 | 0원 (사용량 과금) | EC2 t3.micro 약 $9.5 + ALB 약 $16 → **약 3.6만원** | Fargate 최소 태스크 + ALB → 약 4만원 이상 |
| 트래픽 0일 때 | 0원 | 고정비 그대로 발생 | 고정비 그대로 발생 |
| 롤백 방식 | 별칭 전환 (즉시) | 재배포 또는 AMI 교체 (분 단위) | 태스크 정의 교체 (분 단위) |
| 운영 부담 | OS·패치 없음 | OS 패치, 에이전트 설치 | 이미지 관리 |
| 예산(2만원) 충족 | 충족 | **초과** | **초과** |

**결론**: 저트래픽 환경에서는 사용량 과금 구조인 서버리스가 비용과 복구 속도 모두에서 유리하다.

### 6.5 비용 통제 장치
| 장치 | 방어 대상 |
|---|---|
| API 스로틀링 (10 rps) | 요청 폭주로 인한 사용량 요금 급증 |
| 로그 보존 14일 | 로그 저장 요금 누적 |
| X-Ray 기본 샘플링 | 트레이스 요금 급증 |
| AWS Budgets 알림 (50%/100%/예측 100%) | 예상치 못한 모든 비용 |
| VPC 미사용 | NAT Gateway 고정비 (월 약 6만원) |

## 7. 시스템 설계

### 7.1 적용한 설계 원칙
| 원칙 | 적용 내용 |
|---|---|
| 모듈화 | Terraform을 `app`/`api`/`monitoring`/`notification` 4개 모듈로 분리 |
| 높은 응집도·낮은 결합도 | 각 모듈은 한 가지 관심사만 담당, 모듈 간에는 출력값(ARN 등)으로만 연결 |
| 관심사 분리 | 비즈니스 Lambda와 복구 Lambda 분리, 인프라(Terraform)와 코드 배포(CI) 소유권 분리 |
| 정보 은닉 | 설정은 환경변수·SSM으로 외부화, 코드는 테이블명·버전을 하드코딩하지 않음 |
| 불변성 | Lambda 버전은 한 번 게시되면 변경 불가, 롤백은 새 배포가 아닌 포인터(별칭) 전환 |
| 멱등성 | 복구 Lambda는 현재 버전 = 목표 버전이면 아무 동작도 하지 않음 |
| 최소 권한 | 역할별 IAM 분리 (앱 / 복구 / CI plan / CI deploy) |
| 실패 안전 (Fail-safe) | 스모크 테스트 실패 시 별칭을 전환하지 않아 기존 버전이 계속 서비스 |

### 7.2 아키텍처
```
  GitHub PR ──▶ ci.yml (테스트 · plan)
  main merge ─▶ deploy.yml (apply → 코드 게시 → 스모크 테스트 → 별칭 전환)
                                   │
┌────────┐   ┌──────────────┐   ┌──────────────────┐   ┌──────────┐
│ Client │──▶│ API Gateway  │──▶│ Lambda:live 별칭  │──▶│ DynamoDB │
└────────┘   │  (HTTP API)  │   └────────┬─────────┘   └──────────┘
             └──────┬───────┘            │
                    ▼                    ▼
             ┌─────────────────────────────────────┐
             │ CloudWatch Logs · Metrics · X-Ray    │
             └──────────────────┬──────────────────┘
                                ▼
                        CloudWatch Alarm ①②③
                  ①             │            ②③
                  ▼                          ▼
             EventBridge                   SNS → 이메일
                  ▼                          ▲
          복구 Lambda ──(별칭 롤백)──────────┘
```

### 7.3 구성요소 명세
| 구성요소 | 역할 | 주요 설정 |
|---|---|---|
| API Gateway (HTTP API) | 요청 수신·라우팅·스로틀링 | 10 rps / burst 20, access log |
| 앱 Lambda | 비즈니스 로직 | Python 3.12, arm64, 256MB, 10초, Active Tracing |
| `live` 별칭 | 현재 서비스 버전을 가리키는 포인터 | API 통합 대상 |
| DynamoDB `items` | 데이터 저장 | On-Demand |
| CloudWatch Alarm | 장애 탐지 | 5xx-rate / 5xx-count / p99-latency |
| EventBridge 규칙 | 알람 상태 변화 → 복구 트리거 | 5xx-rate ALARM 전환만 매칭 |
| 복구 Lambda | 자동 롤백 | 별칭 전환, 멱등 처리 |
| SSM Parameter | 마지막 정상 버전 저장 | `/obs-app/last-known-good-version` |
| SNS | 알림 발송 | 이메일 구독 |
| AWS Budgets | 비용 경보 | 월 $10 |

### 7.4 데이터 설계 — `items` 테이블
| 속성 | 타입 | 키 | 제약 | 설명 |
|---|---|---|---|---|
| id | String | PK | UUID v4, 서버 생성 | 아이템 식별자 |
| createdAt | String | | ISO8601, 서버 생성 | 생성 시각 |
| status | String | | `active` \| `archived` | 상태 |
| payload | Map | | 최대 10KB | 사용자 데이터 |

- 접근 패턴이 "ID로 단건 조회"뿐이므로 보조 인덱스(GSI) 불필요

### 7.5 인터페이스 설계 (API 명세)

| 메서드 | 경로 | 요청 | 성공 응답 | 오류 응답 |
|---|---|---|---|---|
| GET | `/health` | - | `200 {"status":"ok","version":"12"}` | - |
| POST | `/items` | `{"payload": {...}}` | `201 {"id":"<uuid>","createdAt":"..."}` | `400` 본문 누락·형식 오류, 10KB 초과 |
| GET | `/items/{id}` | - | `200 {"id":..., "status":..., "payload":...}` | `404` 없음 |

공통 오류 형식: `{"error": {"code": "NOT_FOUND", "message": "...", "requestId": "..."}}`
공통: 모든 응답 헤더에 `x-request-id` 포함 (로그·트레이스와 연결)

### 7.6 자가복구 처리 흐름 (시퀀스)
```
운영자/CI        앱 Lambda        CloudWatch       EventBridge      복구 Lambda        SSM / SNS
   │ 결함 버전 배포   │                 │                 │                 │                 │
   │───────────────▶│ 5xx 증가         │                 │                 │                 │
   │                │────────────────▶│ 5xx-rate 초과    │                 │                 │
   │                │                 │ (5분×2회)        │                 │                 │
   │                │                 │ OK → ALARM ────▶│ 규칙 매칭        │                 │
   │                │                 │                 │───────────────▶│ 정상 버전 조회   │
   │                │                 │                 │                 │───────────────▶│ SSM
   │                │                 │                 │                 │ 현재 ≠ 정상?    │
   │                │◀─────────────────────────────────────────── 별칭 전환 │                 │
   │                │ 정상 버전 서비스  │                 │                 │ 결과 통보 ─────▶│ SNS
   │                │                 │ ALARM → OK      │                 │                 │
```

### 7.7 알람 상태 전이
```
        임계 초과(평가 기간 충족)
   OK ──────────────────────────▶ ALARM ──▶ (①만) 자동 롤백 + 통보
    ▲                               │
    └──────── 임계 이하 복귀 ────────┘
   데이터 없음 = notBreaching (트래픽 없음을 장애로 보지 않음)
```

### 7.8 알람 설계
| 알람 | 조건 | 동작 | 설계 의도 |
|---|---|---|---|
| ① 5xx-rate | 5분 합계 요청 ≥ 10 이고 5xx 비율 > 5%, 2회 연속 | 자동 롤백 + 이메일 | 되돌리기 어려운 조치 → 보수적 |
| ② 5xx-count | 5분 합계 5xx ≥ 3 | 이메일 | 저트래픽 장애 보완 → 민감하게 |
| ③ p99-latency | p99 > 3초, 3회 중 2회 | 이메일 | 원인이 다양해 사람 판단 필요 |
